# Архітектура та модель даних проекту

Цей документ фіксує трирівневу модель даних для формування еталонної бази адрес Старокостянтинівської громади.

---

## 1. Трирівнева модель даних та профіль громади

Робота механізму будується навколо **Профілю громади** (`profiles/hromada.json`, schema 3 — задає назву громади, відповідний РЕМ, `center`/`bbox`, пороги `guards` та 67 населених пунктів із кодами `katottg`, `slug`, координатами `lat`/`lon` і прапорцем `ambiguous_in_rem` для однойменних сіл).

Замість одного змішаного файлу проект оперує **двома незалежними вхідними наборами** та **одним зведеним результатом**:

1. **Набір №1: «Дані Обленерго» (Першоджерело підчерг)**
   - **Джерело:** офіційний сайт / XLSX-переліки АТ «Хмельницькобленерго» (PDF на сайті лише дублює XLSX).
   - **Зміст:** сирі адреси та їхня прив'язка до підчерг (`1.1` – `6.2`).
   - **Призначення:** єдине джерело правди щодо номера підчерги; періодично оновлюється для виявлення змін на сайті обленерго.

2. **Набір №2: «Зовнішній еталон» (Відкриті геодані громади)**
   - **Джерело:** OpenStreetMap / Overpass API (за `osm_relation` із прив'язкою вулиць до сіл і кодами КАТОТТГ) + Visicom Data API (`src/fetch_visicom.py`, локальний кеш із геофільтром ≤ 12 км від координат села для захисту від однойменних сіл).
   - **Зміст:** актуальний перелік населених пунктів і вулиць громади. Дані кешуються локально в `data/set2_external/`.
   - **Призначення та обмеження:** використовується **виключно для валідації та виправлення назв сіл і вулиць** у Наборі №1. Будинки та підчерги беруться з Набору №1.

3. **Результат: «Чиста еталонна база JSON для SvitloSk (schema 2)»**
   - **Механізм формування:** нормалізація вулиць (`src/common/normalize.py`), класифікатор номерів будинків (`src/common/houses.py`, **діапазони не розгортаються**), відстеження стану й змін підчерг (`src/sync_addresses.py`), перевірки безпеки (`src/guards.py`) та валідація за `schema/addresses.v2.json` (`src/build_output.py`).
   - **Формат:** у фінальний JSON потрапляють **лише активні житлові адреси** (`status=active`) з масивом підчерг (`1.1`–`6.2`) і природним сортуванням номерів.

---

## 2. Звірка та виправлення помилок

- Зовнішні сервіси (OpenStreetMap тощо) використовуються **лише на етапі підготовки та періодичної перевірки бази**, а не під час роботи додатку `SvitloSk`.
- Наявність двох окремих наборів дозволяє автоматично виявляти:
  - одруківки та старі назви вулиць у XLSX обленерго;
  - нові або змінені адреси при оновленні першоджерела;
  - прогалини між відкритими даними громади та переліком обленерго.

---

## 3. Формат зберігання, валідація та постачання

Усі дані зберігаються **лише в локальних JSON / JSONL файлах** (без баз даних):

- **Робоче зберігання (`data/`):**
  - `raw_oblenergo/` — останні 10 сирих XLSX + `meta.json`;
  - `set1_oblenergo/` — відфільтрований набір №1;
  - `set2_external/` — локальні кеші OSM і Visicom;
  - `state/` — `addresses.json` (поточний стан кожної адреси), `history.jsonl` (журнал змін підчерг), `snapshots.json`, `backup/` (останні 14 копій);
  - `reports/` — `diff_YYYYMMDD_HHMM.json`, `runs.jsonl`, `profile_check.json`.
- **Правила (`rules/`):**
  - `rules/common/` — спільні (`orthography.json`, `street_types.json`, `house_patterns.json`, `non_residential.json`);
  - `rules/hromada/` — специфічні для громади (`street_renames.json`, `exclude.json`, `house_fixes.json`, `overrides.json`, `manual_additions.json`).
- **Чистий результат (`output/`):**
  1. `addresses.json` — еталонна база schema 2 (перевірена за `schema/addresses.v2.json`).
  2. `subqueue_changes.json` — зміни підчерг за останній запуск.
  3. `excluded_log.json` — журнал виключень із збереженням коментарів.
  4. `needs_review.json` — черга перевірки.
  5. `run_report.json` та `admin_report.html` — звіт запуску й локальна HTML-панель із 3 вкладками (*«Зміни підчерг»*, *«Потребує рішення»*, *«Статус запусків»*).
