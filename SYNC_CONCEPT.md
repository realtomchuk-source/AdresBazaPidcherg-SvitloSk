# Концепція періодичної синхронізації з першоджерелом (`hoe.com.ua`)

Цей документ описує механізм періодичного отримання даних із сайту АТ «Хмельницькобленерго» — спочатку для первинного наповнення **Набору №1 («Дані Обленерго»)**, а згодом для моніторингу змін та перевірки спірних адрес.

---

## 1. Принципи роботи механізму

1. **Першоджерело — XLSX:** Основним джерелом є таблиці Excel (`.xlsx`) зі сторінки `hoe.com.ua/page/pogodinni-vidkljuchennja` для **обраного РЕМ** (за профілем громади; для основного завдання — Старокостянтинівський РЕМ). PDF на сайті лише дублює XLSX і не використовується для парсингу.
2. **Економність (перевірка за хешем):** Повна переобробка запускається лише тоді, коли файл на сайті реально змінився (`ETag` / `Last-Modified` або `SHA-256` хеш файлу).
3. **Захист від збоїв джерела:** Якщо сайт недоступний, повернув помилку або битий/порожній файл — попередній коректний Набір №1 **не перезаписується**.
4. **Дбайливе навантаження (Rate Limiting):** Запити виконуються за розкладом (наприклад, 1 раз на добу або на тиждень) без агресивного сканування.

---

## 2. Етапи роботи

### Етап 1: Первинний збір (Зараз)
1. Скрипт-збирач за параметрами **профілю громади** знаходить актуальне посилання на файл відповідного РЕМ на сторінці `gPV` та завантажує його.
2. Зберігає оригінал файлу (з датою та `SHA-256` хешем) як архівний зліпок.
3. **Фільтрація за межами громади:** Оскільки файл РЕМ може містити населені пункти різних громад, на цьому кроці записи звіряються з еталонним довідником профілю громади (`profiles/hromada.json`):
   - залишаються лише **адмінцентр** та села, що входять до **старостинських округів** обраної громади;
   - кожному селу одразу присвоюється його старостинський округ;
   - населені пункти інших громад відсіюються, а нерозпізнані назви (можливі одруківки в назві села) потрапляють у лог для ручної перевірки.
4. Парсить відфільтровані дані у структурований **Набір №1** (тип/округ, населений пункт, сира назва вулиці, будинок, підчерга).

### Етап 2: Періодична перевірка та виявлення змін (Потім)
1. **Перевірка оновлень:** За розкладом збирач перевіряє, чи змінився файл на сайті (за хешем).
2. **Побудова різниці (Diff):** Якщо файл оновився, новий Набір №1 порівнюється з попереднім:
   - які адреси **додалися**;
   - які адреси **зникли**;
   - у яких адрес **змінилася підчерга**.
3. **Перевірка спірних даних та точковий пошук за адресою:**
   - Адреси, які не вдалося однозначно зіставити з **Набором №2 («Зовнішній еталон»)** або які потребують уточнення, потрапляють у список спірних.
   - На сайті обленерго виявлено окремий інтерактивний сервіс: `https://hoe.com.ua/shutdown/queue` (пошук підчерги за конкретною адресою: населений пункт → вулиця → будинок). У перспективі варто розглянути створення окремого інструменту для точкового запиту до цього сервісу, якщо XLSX-файл виявиться неповним.

---

## 3. Результат роботи механізму

На виході механізм формує:
- оновлений **Набір №1**;
- короткий **звіт про зміни (Diff-лог)**, щоб адміністратор бачив, що саме змінилося на сайті обленерго, перш ніж зміни потраплять у зведену базу для `SvitloSk`.
