# План періодичного моніторингу та обробки зворотного зв'язку

Цей документ описує хронологію періодичних перевірок та концепцію єдиного інструменту моніторингу (`src/monitor.py`) для підтримки актуальності бази адрес Старокостянтинівської громади.

---

## 1. Хронологія періодичного моніторингу

| Періодичність | Що перевіряється | Дія при виявленні змін |
| :--- | :--- | :--- |
| **Щодня / раз на 2–3 дні** | **Сайт Обленерго (`hoe.com.ua`)** | Перевірка `SHA-256` хешу XLSX-файлу РЕМ. Якщо змінився — завантаження, фільтрація за профілем та генерація **Diff-звіту** (додані/видалені адреси, зміна підчерг). |
| **Щодня / раз на 2–3 дні** | **Нові назви сіл (`skipped_settlements`)** | Перевірка через `rapidfuzz`, чи не з'явилися в таблиці РЕМ нові варіанти написання сіл громади. |
| **Раз на місяць** | **OpenStreetMap (Overpass API)** | Оновлення локального кешу **Набору №2** (`--force`) для виявлення нових перейменованих вулиць. |

---

## 2. Єдиний інструмент моніторингу (`src/monitor.py`)

Усі перелічені перевірки об'єднано в один CLI-скрипт `src/monitor.py`, який запускається локально за розкладом через Планувальник завдань Windows і формує єдиний короткий звіт.

### Ручне поповнення та вихідні файли
Усі результати роботи `src/monitor.py` зберігаються локально в теці `output/`:
1. **Основна лаконічна база** — очищені адреси з підчергами для нової версії `SvitloSk`.
2. **Файл виключень** — відсіяні однозначні винятки (довгі назви, нежитлові об'єкти).
3. **Файл ручних доповнень** (`manual_additions.json`) — адреси та підчерги, внесені вручну, які автоматично підтягуються в основну базу.
4. **Файл помилок / незбігів** — записи, які система не змогла опрацювати автоматично (для ручної правки через словники/правила).

---

## 3. Рекомендації щодо оптимізації форми в `SvitloSk`

Для нової версії додатку `SvitloSk` (сторінка «Підчерга») варто врахувати такі покращення форми зворотного зв'язку:
- **Вибір округу та села зі списку:** використовувати наш єдиний довідник профілю громади, щоб уникнути помилок у назвах сіл.
- **Підказка схожих вулиць перед відправкою:** якщо користувач вводить назву вулиці, показувати схожі вже наявні вулиці (це зменшить кількість дублікатів через `вул.` / `пров.` чи ініціали).

## 4. Автоматизація (Планувальник завдань Windows) і Visicom

- **Планувальник Windows:** завдання `SvitloSk-AddressMonitor` (реєструється через `scripts/register_task.ps1`, видаляється через `scripts/unregister_task.ps1`) запускає `scripts/run_monitor.ps1` щодня о **07:30** і **19:30** без прав адміністратора.
- **Коди виходу `src/monitor.py`:** `0` (оновлено), `10` (`unchanged` — sha256 не змінився), `2` (`guard_failed`, стан і `output/` не змінені), `5` (паралельний запуск заблоковано `data/state/.lock`), `1`/`3` (помилка). У `meta.json` та `run_report.json` фіксується HTTP-заголовок `Last-Modified` файлу обленерго.
- **Захист стану:** ручні виключення з `rules/hromada/exclude.json` переводять адресу в `status = "excluded"` одразу за 1 прогін; раптове зникнення з XLSX переводить у `gone` після 2 прогонів; для сіл із `ambiguous_in_rem: true` невідомі вулиці автоматично підсвічуються в `needs_review.json` (`ambiguous_village_street`).
- **Visicom Data API (реалізовано):** `src/fetch_visicom.py` автоматично перевіряє нерозпізнані в OSM сільські вулиці за ключем `VISICOM_API_KEY` із `.env` (з геофільтром ≤ 12 км від села) та кешує їх у `data/set2_external/starokostiantyniv_visicom.json` (деталі — у [VISICOM_GUIDE.md](VISICOM_GUIDE.md)).
- **На майбутнє:** точкова перевірка підозрілих номерів будинків (`adr_address`) через Visicom та кешування координат (`lat/lon`) для майбутньої PWA.
